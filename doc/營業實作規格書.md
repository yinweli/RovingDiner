## 一、設計總綱

三個需求（核心與顯示解耦、完整單元測試、測試資料做法）指向同一核心決策：
**營業核心是一個純邏輯、單執行緒、決定性（deterministic）的狀態機，所有對外的東西都走邊界介面**。
守住這條線，C# 重寫、單元測試、測試資料三件事會同時變簡單。

四條鐵則：

1. **核心零 I/O、零框架依賴**：`game` 核心不 import Bubble Tea、不碰終端機、不開 goroutine、不碰全域時間/亂數。只依賴介面。
2. **決定性**：同 `seed` + 同玩家輸入 = 同一局。所有隨機來源（洗牌、隨機顧客／手牌、額外發動次數區間、抽獎）共用單一注入的 `Rander`（seeded PRNG），是回歸測試與 bug 重現的基礎（顯示層如何顯示 seed 見顯示規格書 §3.1）。
3. **yield-per-unit 事件流**：核心每跑「一個單位」（一個命令／一次觸發／一次 phase 切換／一個玩家動作）就吐一個事件。快速／慢速／步進只是同一條事件流的不同消費速率（消費端設計見顯示規格書 §3）。
4. **可移植子集明確**：只有 `expr` + `game` + instance 模型 + `defines` 需移植到 C#；`infra`、`app/tui` 是 Go-only 基礎設施，不移植。
   靜態表格層（Card/Guest/Skill/Effect/Seat/Setting/Award）由 [Sheeter](https://github.com/yinweli/Sheeter) **同時生成 Go 與 C# 版**，移植時不用手抄 → 真正要移植的只剩 `expr` + `game` 邏輯。
5. **單一真相 + 單向投影**：引擎是唯一真相，持有全部 instance 與容器（純可序列化資料、零顯示依賴）；前端（TUI／Unity）是純投影，靠事件流 + `InstanceID` 對照表更新畫面，**不持有規則狀態的第二份拷貝**。詳見第四節之二。

## 二、套件結構

沿用 DiceBattle-server 的命名直覺（`defines` / `this` receiver / `sheet` 既有；基礎設施層改名為 `infra`），
但因為是純規則引擎、無 DB／網路，砍掉 `apis`／`querys`／`modules`，改以演算法子系統分包。

```text
RovingDiner/
├─ cmd/
│  └─ tui/                  瘦進入點 main.go：flag 解析（seed、replay 檔）+ 組裝後呼叫 app
├─ app/
│  └─ tui/                  TUI 應用本體：Bubble Tea Model/Update/View + engine adapter
│                           （未來 Unity 版＝C# 那側的另一個「app」，消費同一核心）
├─ infra/                   sheet 載入（組裝出 *sheeter.Sheeter）、PRNG 來源（Go 基礎設施，不移植 C#）
│                           與 sheet/ 同層的基礎設施層；非 internal（與既有 sheet/ 公開層一致）
├─ internal/                ★可移植核心邊界（這三個包才要搬去 C#）
│  ├─ defines/              常數、列舉、type alias；觸發時機／命令／屬性／命令對象 名稱表
│  ├─ expr/        ★移植     運算式引擎：lexer → parser → AST → evaluator
│  │                         對「條件對象」只認一個 Resolver 介面（保持 game-agnostic）
│  ├─ game/        ★移植     營業核心（純邏輯），單一 package、依關注點分檔：
│  │   ├─ interface.go       行為邊界介面：Operator / Presenter / Rander（靜態資料直接吃 *sheeter.Sheeter）
│  │   ├─ award.go           抽獎群組衍生索引（核心預建；取代舊 Dater 的預處理）
│  │   ├─ runtime.go         一場營業的聚合狀態（全域屬性 + 全部容器 + 結算旗標）
│  │   ├─ instance*.go       Game/Card/Guest/Effect/Action/Value 實例 + 容器（引擎持有）
│  │   ├─ property*.go       屬性註冊表（把全域／引用屬性、查詢函式綁進 expr.Resolver）
│  │   ├─ command*.go        命令解譯（屬性修改 + 操作命令）
│  │   ├─ selector*.go       命令對象解析（guestPick/deckTop/handAll…；含 N 邊界／退化／filter／deckTop auto-shuffle）
│  │   ├─ effect*.go         效果佇列：堆疊處理／觸發時機／推進／清理
│  │   └─ flow*.go           phase 狀態機 + 啟動技能（含目標類型 self 綁定）+ 執行結算
│  └─ ...
├─ sheet/ sheetdata/ gamedata/    （已存在，沿用既有 Sheeter pipeline）
└─ testdata/                測試 fixture / scenario / golden（做法見第七節）
```

- `cmd/` 保持瘦（只有 main + flag + 組裝）；TUI 本體放 `app/tui`，所以 `cmd` 不會肥。此分法對齊 DiceBattle-server（`cmd/` 瘦進入點、`app/` 應用本體）。
- 命令（verb）與命令對象（作用對象解析）拆成 `command*.go` 與 `selector*.go` 兩個前綴：兩者執行時雖一起出現，但屬不同關注點。**命令對象刻意不叫 `target`**，以免與 spec【八】的「目標類型(TargetType)」撞名。
  - 命名定為 `selector`（非保留字，可同時當檔名前綴與識別碼 `Selector` / `selectorGuest`）。語意是「用篩／抽／查／切各種方式產出作用對象集合」，比 `filter` 廣（`filter` 已是 spec【二十四】命令對象內部「卡牌編號篩選」的子術語，且 `deckTop` 會 mutate，不符 filter 唯讀語意）。

**為什麼 `game` 是單一 package 而非再拆細**：flow／command／effect／settlement 互相讀寫同一份 runtime 狀態，
拆成多 package 會逼出大量 getter 或循環 import。檔案分檔（`command*.go` 等）已足夠導覽，又免去 Go 的 import 摩擦。
`expr` 例外獨立，因為它真的零遊戲依賴、可單獨測。

**`expr` 與 `game` 的解耦**：`expr` 只懂語法與運算，遇到「條件對象」（`morale`、`self.calm`、`drawLast.cardID`、
`tableCount('>=',2)`…）時呼叫一個 `Resolver` 介面取值。`game` 實作 `Resolver`，把【二十三、屬性清單】的綁定塞進去。
這樣 expr 100% 可移植，且能脫離遊戲跑語法／運算測試。

## 三、核心引擎的內部分層

由內而外、依賴單向：

| 層       | 檔案                        | 職責                                                                                              | 對應 spec                 |
|:---------|:----------------------------|:--------------------------------------------------------------------------------------------------|:--------------------------|
| 狀態     | `instance*.go` `runtime.go` | Value/Game/Card/Guest/Effect/Action 實例與 10 個容器；`Value` 帶 `Value+Lock`（鎖定計數）統一語意 | 【五】【六】              |
| 運算式   | `expr/`                     | 完整運算式（算術+比較+邏輯+三元）、四捨五入 half-away-from-zero、評估失敗回傳狀態                 | 【二十七】【二十六】      |
| 屬性     | `property*.go`              | 全域屬性／卡牌引用／顧客引用／查詢函式 的讀寫綁定；餐廳士氣值 `-=` 特例                           | 【二十三】【十七.1】      |
| 命令     | `command*.go`               | 屬性修改命令 + ~60 個操作命令（verb）                                                             | 【十七】【二十五】        |
| 命令對象 | `selector*.go`              | ~35 個命令對象解析（作用對象集合；含 N 邊界／退化／filter／deckTop auto-shuffle）                 | 【二十四】                |
| 效果     | `effect*.go`                | 效果佇列、[堆疊處理]、觸發時機、推進效果、清理效果、免疫閘門                                      | 【七】【十~十六】【二十】 |
| 流程     | `flow*.go`                  | 6 個 phase 狀態機 + 啟動技能 + 執行結算 + 終止判定 + 結算旗標重入防護                             | 【十九】【二十】          |

三個易混的「解析對象」概念，分屬不同層、不同時機，務必分清：

| 概念                  | 是什麼                                                   | 時機                    | 放哪                     |
|:----------------------|:---------------------------------------------------------|:------------------------|:-------------------------|
| 命令（verb）          | ~60 操作命令 + 屬性修改                                  | 執行命令時              | `command*.go`            |
| **命令對象解析**      | `guestPick`／`deckTop`／`handAll`… 解析「這次作用到誰」 | 執行命令時（第 1 參數） | `selector*.go`           |
| 目標類型（self 綁定） | 新選／沿用／隨機 顧客／手牌                              | 效果建立時（啟動技能）  | `effect*.go`／`flow*.go` |

會咬到設計的細節：

- **`Value` 雙欄模型**：所有可變屬性都是 `{Value, Lock}`。`@`／`#` 改 `Lock`，帶值賦值在 `Lock>0` 時 no-op。
  做成共用型別，否則 60 個命令會各寫各的。
- **結算重入**：`執行命令` 後若 `結算旗標==false` 會呼叫 `執行結算`，而結算又會觸發時機 → 跑命令。
  `結算旗標` 必須是 runtime 狀態、且流程要能安全重入。
- **暫停點**：玩家行動主迴圈、目標選取（新選顧客／手牌）、命令對象 `*Pick`、手牌上限棄牌——
  全部收斂成對 `Operator` 介面的同步呼叫，核心不需要知道對方是 TUI 還是測試腳本。

## 四、解耦的關鍵：邊界介面

核心只認三個**行為**介面，TUI 與測試各自提供實作。**靜態表格不走介面**：
Sheeter 已雙語言生成 `*sheeter.Sheeter`（Go／C# 形狀一致），它本身就是核心的靜態資料 port，
核心直接以 `data.Card.Get(id)` 查詢；衍生索引（如抽獎依群組聚合）由核心預建（見 `award.go`）。

> 為何不再用 `Dater` 介面包一層：核心回傳型別本就是 `*sheeter.Card` 等生成型別，介面並未真正隔離生成碼；
> 而每新增一張表就要改一次介面，其唯一收益（抹平 Go／C# 存取差異）正是 churn 來源。
> 既然 `Sheeter` 已是跨語言資料 port，直接使用即可——Go 的 `reader.Get(key)`（查無回 nil）為統一存取形狀，
> C# 端對應 reader 亦提供等價的 `Get`。衍生邏輯（Award 聚合等）移入核心成為可移植邏輯。

```go
// Rander：唯一亂數來源（單一 seeded PRNG）
type Rander interface {
    Intn(n int) int
    Shuffle(n int, swap func(i, j int))
    Weighted(weight []int32) int          // 抽獎 weighted random
}

// Operator：玩家輸入（所有「暫停流程」點）
type Operator interface {
    PlayerAction(runtime *Runtime) Action      // 出牌 X / 結束
    PickGuest(source []*Guest, count int) []*Guest   // 新選顧客 / guestPick / nearPick / samePick
    PickCard(source []*Card, count int) []*Card      // 新選手牌 / *Pick 牌堆類
    PickDiscard(source []*Card, over int) []*Card    // 手牌上限棄牌
}

// Presenter：事件流輸出（yield-per-unit；步進時可阻塞）
type Presenter interface {
    Emit(eventData EventData)   // 一個命令／一次觸發／一次 phase 切換／一個玩家動作 = 一個 EventData
}
```

**核心怎麼跑**：`game.Run(runtime, data, rander, operator, presenter)`（`data` 為 `*sheeter.Sheeter`），內部就是 spec【十九】【二十】的同步流程。
需要玩家輸入時 call `operator.PickXxx(...)` 並阻塞等回傳；每跑一個單位 call `presenter.Emit(...)`。
**核心本身完全同步、單執行緒、無 channel。**

**TUI adapter（Go-only）**：在背景 goroutine 跑 `game.Run`，用 channel 把 `Operator`／`Presenter` 的呼叫橋接到
Bubble Tea 的 Elm loop。步進＝`Presenter.Emit` 在 channel 上阻塞，等使用者按 `[N]` 才放行。
**goroutine + channel 只活在 adapter，核心碰不到** → C# 重寫時 adapter 整個丟掉、核心原樣搬。

**C# 對應**：三個行為介面 → 三個 C# interface，靜態資料 `*sheeter.Sheeter` → C# 生成的 `Sheeter`，`game.Run` → 一個同步方法。測試腳本與 golden 機制也能一起搬。

### 四之二、狀態歸屬與前端投影（Unity／TUI 共用）

**問題**：移植到 Unity 時，若 instance／容器由前端持有，前端要同步「規則資料」與「GameObject」兩份東西，很難維護。

**根因**：難點不在「核心持有資料」，而在「資料雙向同步」。先把兩種狀態拆開：

- **規則狀態（rules-state）**：`sate`／`calm`／鎖定計數／實例效果列表／所在容器／`InstanceID`…… 引擎每個 tick 狂讀狂寫。
- **顯示狀態（view-state）**：GameObject 的 transform／sprite／動畫／版面位置…… 前端的東西。

耦合只在「instance↔GameObject 互持參考」或「兩邊都能改同一份資料」時才發生。用穩定的 `InstanceID`（spec【五】各實例本就有）連結，耦合即不存在。

**做法：單一真相 + 單向事件投影**（不採「前端實作佇列」）：

```text
引擎（唯一真相）──事件流──▶ 前端（純投影）
  持有 instance + 容器           Map<InstanceID, View/GameObject>
  每跑一個單位 Emit 細粒度事件     收事件 → 建立／移動／更新／銷毀 View
```

- 事件夠細：`卡牌 1234 抽牌牌堆→手牌`、`顧客 5678 sate 30→18`、`效果 9001 入佇列`、`卡牌 1234 銷毀`。
- 前端**只**維護 `InstanceID → View` 對照，收事件改畫面；**不持有規則狀態的第二份拷貝** → 只有一份真相、單向流動 → 「同步兩份資料」的痛點消失。
- **TUI 與 Unity 共用同一個 `Presenter` 事件流**，一套設計餵兩個前端。
- 為什麼不採「前端實作佇列」：引擎每 tick 要讀寫大量實例屬性，若佇列／實例由前端經介面持有，邊界會極度 chatty，且把規則狀態漏進前端層（規則／顯示混淆）；它解決的「資料重複」對本遊戲資料量根本不是問題。

**投影事件分類（`EventData` 設計草案）**：

| 類別           | 例                                           | 前端反應                             |
|:---------------|:---------------------------------------------|:-------------------------------------|
| lifecycle      | 實例 建立／銷毀（卡牌／顧客／效果）          | 生成／回收 View                      |
| container-move | 卡牌移動牌堆、顧客入座／離場／遊蕩／卡牌化   | View 換容器、播移動動畫              |
| property-delta | `sate`／`calm`／`score`／鎖定計數 變化       | 更新數字、播受擊／加值表演           |
| trigger        | 觸發時機到達、某效果觸發                     | 高亮來源、播效果表演（spec【十八】） |
| phase          | phase 切換（不另立日誌行，併入下一事件前綴） | 更新狀態列                           |

> 選項（暫不採）：核心對容器存取走 `Container[T]` 介面、**預設 in-core 實作**，保留未來讓外部接管儲存的seam。預設關閉，因為事件投影已達成解耦。

## 五、顯示／操作層（TUI，不移植）

`app/tui`（本體）+ `cmd/tui`（瘦進入點），Bubble Tea + Lip Gloss + Bubbles，照顯示規格書 §4~§7。只做三件事：

1. 實作 `Operator`（鍵盤 → 選取／動作）、`Presenter`（EventData → 事件日誌 + 盤面渲染）。
2. 跑背景 goroutine 驅動核心，channel 橋接。
3. `[Space]` 快速／慢速／步進切速率、`seed` flag（決定性，供重現 bug；營業中不存檔、不重播）。

核心吐的 `EventData` 要自帶表演資訊與目標（spec【十八】），TUI 才能在正確目標上表演，而核心不需要知道任何畫面細節。

## 六、Sheet 整合

沿用既有 `sheeter` pipeline，不動生成碼。`infra` 提供 `Loader`（讀 `sheetdata/*.json`）與 `Load(dir)`：
`Load` 內部 `NewSheeter(loader).FromData()` 組裝出 `*sheeter.Sheeter` 並回傳，核心直接吃這份生成的跨語言資料 port。
載入後的衍生索引（Award 依 group 聚合，未來如 Seat 同桌／鄰桌反查、Skill→Effect 展開）**移入核心**（`award.go` 等），
作為可移植邏輯由引擎初始化時建一次快取——而非放在不移植的 `infra`。

## 七、測試策略

統一用 **testify suite**（`Suite{Feature}` + `this` receiver），對齊 DiceBattle。

### 7.1 一律 in-memory builder（三層同一心智模型）

✅ **三層測試全部用 in-memory builder 直建資料**（不採 embedded fixture、不採 scenario/golden DSL）。
三層只差「建多少、跑多深」：

| 層 | 建什麼                                                    | 跑什麼                                          | 驗什麼             |
|:---|:----------------------------------------------------------|:------------------------------------------------|:-------------------|
| L1 | 幾個 entity（builder）                                    | 直接戳子系統（expr／command／selector／effect） | 單點行為           |
| L2 | entity + 初始容器                                         | 單一 phase／獨立流程（啟動技能／執行結算）      | 流程片段           |
| L3 | 完整資料 + 初始牌堆／排隊／前置技能 + scripted `Operator` | `game.Run` 跑到結算                             | 最終盤面／事件序列 |

理由：沒有重播需求、主要作者是工程／AI（非企劃），scenario 檔的好處用不到；單一做法心智負擔最低、type-safe、refactor 友善。

### 7.2 核心紀律：共用工廠，不共用實例

上一個專案用 `testdata/prefab*` 共用**建好的實例**，後期出現兩個病：①搞不清某筆資料為誰存在 ②一改壞一片。
根因是 tests 透過共用的**可變實例**互相耦合。對策——**去重去在「builder + 預設值」這層，不要去在「實例」這層**：

- builder 給一個**中性合法預設**（空白卡／普通顧客／無效果效果），test 只 inline 寫**它在乎的欄位**，其餘吃預設。
  - → 「為何存在」自明：被 set 的就是這 test 的重點，沒 set 的就是「不在乎」。
  - → 「改一個壞一片」消失：tests 各自 build、不共用可變實例，物理上互不影響。
  - → 去重沒丟：預設值吸收 boilerplate，重複量小且安全。
- **共用範圍越窄越好**：test-local ＞ 同檔／同 suite local ＞ 全專案。禁止再養全域 prefab 垃圾吸鐵；
  「一族相關 test 的共同基底」放在那個 test 檔／suite 內。
- builder **自動發唯一 ID**；test 用變數綁引用（`card := build.Card().Effect(effA)`），不手管全域 ID 表。
- 只共用「工廠／預設值／角色明確的填充料」（如 `build.FillerCard()`），不共用「帶劇情的實例」。

### 7.3 共用測試基建（放 `testdata/` package）

位置沿用 DiceBattle 的根層 `testdata/`（被明確 import 時照常編譯；`testdata` 特殊規則只影響 `./...` 萬用展開）。
**內容換成工廠，不是 prefab 實例庫**：

- `build.Guest/Card/Effect/Skill/Setting/Award`：中性預設 + inline override + 自動 ID。
- `scriptOp(Play(cardA), Pick(guestX), End())`：scripted `Operator`，把玩家輸入排成佇列。
- `recordPresenter()`：錄事件流 + matcher，給 L3 驗 spec 的觸發時機／結算順序。
- `assemble(...)`：把 builder 產物組成 `Runtime`（初始牌堆／排隊／前置技能／seed）。

L3 若要廣域回歸，可**選擇性**對事件日誌做 golden 字串 snapshot（per-test 選項，非必備基建）。
單一 seeded `Rander` 確保 L3 決定性、assertion 穩定。

## 九、里程碑建議

與顯示規格書 §9 對齊，但核心優先：

### 已敲定／已釐清

- ✅ **測試資料**：三層全用 in-memory builder；共用工廠不共用實例；基建放 `testdata/`（builder／scriptOp／recordPresenter／assemble）。詳見第七節。
- ✅ **核心分包粒度**：**單一 `game` package、依關注點分檔**（不再拆 `command`／`effect`／`flow` 子 package）。理由：flow／command／effect 互相讀寫同一份 runtime 狀態，拆 package 會逼出大量 getter 或循環 import；檔案分檔已足夠導覽。`expr` 仍獨立（零遊戲依賴）。
- ✅ **解耦模型**：**邊界介面 + 同步驅動**（非 step function）。需求已確認：營業中不存檔、不重播 → step function 的「暫停點可序列化」優勢用不到。
  - 直譯 spec【十九】【二十】巢狀流程；暫停＝阻塞呼叫 `Operator`，一對一對應 C#；步進＝阻塞 `Presenter.Emit`；測試＝scripted `Operator`。
  - 接受的取捨：暫停狀態活在 call stack → **營業中無法序列化**（符合「不能存檔」）。**營業邊界**（開始前／結束後）call stack 空、runtime 是純資料，仍可整包序列化 → 未來「局與局之間存檔」不受影響。
  - 單一 seeded `Rander` 仍保留（供 golden 測試與重現 bug，與存檔／重播無關）。

- ✅ **狀態歸屬**：引擎持有 instance／容器（純可序列化資料）+ **單向事件投影**；前端不持有規則狀態第二份拷貝。不採「前端實作佇列」。詳見第四節之二。（保留 `Container[T]` seam 為未來備案，預設 in-core，目前不啟用。）
- ✅ **命令對象命名**：`selector`（檔名 `selector*.go`、識別碼 `Selector`／`selectorGuest`）。非保留字；語意比 `filter` 廣，且避開 `target`（目標類型）與 spec 既有「filter 規則」子術語的撞名。
- ✅ **目錄結構**：`cmd/`（瘦進入點）+ `app/tui`（TUI 本體）+ 根層 `infra/`（基礎設施，與 `sheet/` 同層）+ `internal/{defines,expr,game}`（可移植核心邊界）。`cmd` 不會肥。
- ✅ **命令 vs 命令對象分檔**：`command*.go`（verb）與 `selector*.go`（作用對象解析）拆開。
- ✅ **靜態資料移植**：Sheeter 雙語言生成，靜態表格層 Go／C# 皆免手抄。
