## 一、設計總綱

三個需求（核心與顯示解耦、完整單元測試、測試資料做法）指向同一核心決策：
**營業核心是一個純邏輯、單執行緒、決定性（deterministic）的狀態機，所有對外的東西都走邊界介面**。
守住這條線，核心與顯示解耦、單元測試、測試資料三件事會同時變簡單。

四條鐵則：

1. **核心零 I/O、零框架依賴**：營業核心（`cores`／`rules`／`games`）不 import Bubble Tea、不碰終端機、不開 goroutine、不碰全域時間/亂數。只依賴介面。
2. **決定性**：同 `seed` + 同關卡 + 同玩家輸入 = 同一局。所有隨機來源（洗牌、隨機顧客／手牌、額外發動次數區間、抽獎）共用單一注入的 `Rander`（seeded PRNG），是回歸測試與 bug 重現的基礎（顯示層如何顯示 seed 見顯示規格書 §3.1）。
3. **yield-per-unit 日誌流**：核心每跑「一個單位」（一個命令／一次觸發／一個玩家動作）就吐**一拍 0..n 行最終日誌行**（`Emit(line ...string)`；發射＝有話要說，無空拍）。快速／慢速／步進只是同一條日誌流的不同消費速率（消費端設計見顯示規格書 §3）。
4. **單一真相 + 停點直讀**：引擎是唯一真相，持有全部 instance 與容器（純可序列化資料、零顯示依賴）；前端（TUI）在引擎停點間唯讀直讀盤面渲染，**不持有規則狀態的第二份拷貝**；日誌流供敘事、步進節拍與 golden 比對。詳見第四節之二。

## 二、套件結構

沿用 DiceBattle-server 的命名直覺（`this` receiver、`sheet` 既有；基礎設施層改名為 `infra`），
但因為是純規則引擎、無 DB／網路，砍掉 `apis`／`querys`／`modules`，改以演算法子系統分包。
核心採**引擎本體 + 詞彙層 + 對外介面**分層：`cores` 為營業引擎本體（資料模型 + 驅動引擎 `Game`，單向 import `exprs`），
`rules` 為命令語言詞彙層（屬性讀寫／操作命令／命令對象／內建函式的詞彙表與行為 + 效果流程，單向 import `cores`／`exprs`），
`games` 為對外介面層（`Parse`／`Validate`／`Run`，單向 import `rules`／`cores`／`exprs`）；
依賴呈 `games → rules → cores → exprs` 單一直線；運算式對遊戲值的回呼經 `exprs.Resolver` 介面反轉（`cores.Game` 實作、`exprs` 反向不依賴），全鏈無環。
詞彙以 `rules` 的套件層 map 字面值為單一定義點，建構 `Game` 後經 `rules.Register` 一次裝備進其私有詞彙表（裝備後唯讀、等同常數）。

- `cmd/` 保持瘦（只有 main + flag + 組裝）；應用本體放 `app/{rodi,roditool}`（app 子目錄名跟著 cmd 子目錄名走），所以 `cmd` 不會肥。此分法對齊 DiceBattle-server（`cmd/` 瘦進入點、`app/` 應用本體）。
- 命令（verb）與命令對象（作用對象解析）分屬 rules 的 `command.go` 與 `selector.go`：兩者執行時雖一起出現，但屬不同關注點。**命令對象刻意不叫 `target`**，以免與 營業規格書【八、目標類型】的「目標類型(TargetKind)」撞名。
  - 命名定為 `selector`（非保留字，可同時當檔名與識別碼 `Selector` / `selectorGuest`）。語意是「用篩／抽／查／切各種方式產出作用對象集合」，比 `filter` 廣（`filter` 已是 營業規格書【二十四、命令對象清單】命令對象內部「卡牌編號篩選」的子術語，且 `deckTop` 會 mutate，不符 filter 唯讀語意）。

**為什麼這樣拆 `cores` + `rules` + `games`（引擎本體 + 詞彙層 + 對外介面）**：`cores` 收齊營業引擎本體（資料模型 + 驅動引擎 `Game`），
`rules` 收齊命令語言的規則內容（詞彙表與行為 + 效果流程），`games` 只留對外函式（`Parse`／`Validate`／`Run`）。
用 Go 的 acyclic import 把依賴壓成 `games → rules → cores → exprs` 一條直線——
讀 `games` 即知對外能做什麼；規則內容都在 `rules`，每詞條一個吃 `game *cores.Game` 的具名自由函式，只經 `cores` 公開面（`Get*`／`Locate*`／容器方法）操作狀態；
引擎機制（分派、狀態、原語）都在 `cores`，不 import `rules`／`games`、永不反向依賴詞彙與對外層。
詞彙表為 `Game` 私有成員（裝備制）：`rules` 的 map 字面值是單一定義點，`rules.Register` 於建構後一次裝備、裝備後唯讀。
`exprs` 維持獨立第四包，因為它是零遊戲依賴的運算式語言、可單獨測；其對遊戲值的回呼經 `exprs.Resolver` 介面反轉、由 `cores.Game` 實作。

**`exprs` 的解耦**：`exprs` 只懂語法與運算，遇到「條件對象」（`morale`、`self.calm`、`drawLast.cardID`、
`tableCount('>=',2)`…）時呼叫一個 `Resolver` 介面取值，內建函式（`min`／`max`…）亦由外部注入。
`cores.Game` 委派實作 `Resolver`（讀寫行為由 `rules` 的 `attr*.go` 詞條裝備）、內建函式由 `rules`（`builtin.go`）裝備進 `Game`、求值期經 `Game.Env()` 帶入，把營業規格書【二十三、屬性清單】【二十六、內建函式清單】的綁定塞進去。
這樣 `exprs` 零遊戲依賴，且能脫離遊戲跑語法／運算測試。

三個易混的「解析對象」概念，分屬不同層、不同時機，務必分清：

| 概念                  | 是什麼                                                   | 時機                    | 放哪                   |
|:----------------------|:---------------------------------------------------------|:------------------------|:-----------------------|
| 命令（verb）          | ~60 操作命令 + 屬性修改                                  | 執行命令時              | `rules/command*.go`    |
| **命令對象解析**      | `guestPick`／`deckTop`／`handAll`… 解析「這次作用到誰」 | 執行命令時（第 1 參數） | `rules/selector.go`    |
| 目標類型（self 綁定） | 新選／沿用／隨機 顧客／手牌                              | 效果建立時（啟動技能）  | `rules/effectStart.go` |

會咬到設計的細節：

- **`Value` 雙欄模型**：所有可變屬性都是 `{Value, Lock}`。`@`／`#` 改 `Lock`，帶值賦值在 `Lock>0` 時 no-op。
  做成共用型別，否則 60 個命令會各寫各的。
- **結算重入**：`執行命令` 後若 `結算旗標==false` 會呼叫 `執行結算`，而結算又會觸發時機 → 跑命令。
  `結算旗標` 必須是 runtime 狀態、且流程要能安全重入。
- **暫停點**：玩家行動主迴圈、目標選取（新選顧客／手牌）、命令對象 `*Pick`、手牌上限棄牌——
  全部收斂成對 `Operator` 介面的同步呼叫，核心不需要知道對方是 TUI 還是測試腳本。

## 四、解耦的關鍵：邊界介面

核心只認三個**行為**介面（`Operator`／`Presenter`／`Rander`，定義於 `cores/define.go`），TUI 與測試各自提供實作。**靜態表格不走介面**：
Sheeter 生成的 `*sheeter.Sheeter` 本身就是核心的靜態資料 port，
核心經 `GetSheet()` 直接以 `sheet.Card.Get(id)` 查詢；衍生索引（抽獎依群組聚合、效果命令預編譯）由核心於 `NewData` 預建一次（`cores/data.go` 的 `Data` 聚合；效果命令編譯經 `Compiler` 由 games 注入）。

> 為何不用 `Dater` 介面包一層：核心回傳型別本就是 `*sheeter.Card` 等生成型別，介面並未真正隔離生成碼，
> 反而每新增一張表就要改一次介面，是 churn 來源。直接用 `Sheeter` 的 `reader.Get(key)`（查無回 nil）即可；衍生邏輯（Award 聚合等）移入核心。

```go
// Rander：唯一亂數來源（單一 seeded PRNG）
type Rander interface {
    Intn(n int) int
    Shuffle(n int, swap func(i, j int))
    Weighted(weight []int32) int          // 抽獎 weighted random
}

// Operator：玩家輸入（所有「暫停流程」點）
type Operator interface {
    PlayerAction(game *Game) *Card      // 玩家行動:出牌回該手牌卡、nil 即玩家結束
    PickGuest(source []*Guest, count int) []*Guest   // 新選顧客 / guestPick / nearPick / samePick
    PickCard(source []*Card, count int) []*Card      // 新選手牌 / *Pick 牌堆類
    PickDiscard(source []*Card, over int) []*Card    // 手牌上限棄牌
}

// Presenter：日誌流輸出（yield-per-unit；步進時可阻塞）
type Presenter interface {
    Emit(line ...string)   // 一個語意單位（一個命令／一次觸發／一個玩家動作）= 一拍 = 0..n 行最終日誌行
}
```

**核心怎麼跑**：`games.Run`（M16）內部以 `cores.NewGame(seed, stageID, data, operator, rander)` 建營業實例（seed 與關卡編號同為本場身分；`data` 為 `cores.NewData(sheet, compiler)` 聚合）、`rules.Register` 裝備詞彙後，驅動 rules 的 `runPhase` 推進 營業規格書【十九、核心流程】【二十、獨立流程】的同步流程；開局盤面由 `phaseGameStart` 依關卡編號自關卡表格建置。
需要玩家輸入時 call `operator.PickXxx(...)` 並阻塞等回傳；每跑一個單位 call `presenter.Emit(...)`。
**核心本身完全同步、單執行緒、無 channel。**

**TUI stepper（暫停機；M23 拍板，原 adapter 橋接退役）**：`games` 拆建造與驅動——`Build` 回 `*cores.Game`、`Loop` 驅動到停機、`Run = Loop(Build(…))` 原樣保留（測試與 golden 用）。TUI 把 `Loop` 跑在交棒 goroutine 上：`Emit` 送出行組後**停棒等放行**，`Next()`＝放行一拍＋收下一筆（行組∣終局）；`Next` 只在 Bubble Tea 的 `Update` 內同步呼叫（Update／View 跑同一條 goroutine）→ **TUI 在看畫面時引擎必停在事件邊界**，盤面直讀 `*cores.Game` 不需鎖。步進／快慢（M25）只是呼叫 `Next` 的節奏，引擎端零改動：快／慢＝timer Cmd 排拍（訊息蓋世代章，切模式世代＋1 即作廢在途舊拍，防模式切換競態與雙鏈）、步進＝不排拍等 `[N]`（自動模式下 `[N]` 不插拍）；模式為跨組件 UI 狀態歸 model 持有（推進迴圈、狀態列模式欄與 `[N]` 門控同源），終局後靠 `Next` 防呆自然 no-op、零特判。
**goroutine + channel 只活在 stepper，核心碰不到**——核心因此維持同步、單執行緒，可被 scripted `Operator` 直接測試。

### 四之二、狀態歸屬與日誌流

**問題**：若前端為了渲染而持有第二份規則狀態，就要同步「規則資料」與「畫面物件」兩份東西，很難維護。

**根因**：難點不在「核心持有資料」，而在「資料雙向同步」。先把兩種狀態拆開：

- **規則狀態（rules-state）**：`sate`／`calm`／鎖定計數／實例效果列表／所在容器／`InstanceID`…… 引擎每個 tick 狂讀狂寫，歸引擎。
- **顯示狀態（view-state）**：游標／捲動／模式／樣式…… 前端的東西，歸組件自持。M26 落地形態：游標存 index、讀取時夾界（盤面拍間會變，指標當游標會懸空）；盤面組件契約長成 `View(game, width, focus)`＋`Move(game, key)`＋`Item(game)`（游標移動語意隨區自持、`Item` 回游標下實例指標供 `[Enter]` 辨型開檢視 modal）；跨組件 UI 狀態（聚焦區、速率模式、modal 堆疊與捲動偏移）歸 model 持有。modal 開啟時暫停消費（世代作廢在途拍、關閉依當前模式恢復），內容停點直讀、指標穩定。

**做法：單一真相 + 停點直讀**（M23 拍板；原 M20–M22 的「單向事件投影＋世界鏡像」隨暫停機退役）：

```text
引擎（唯一真相）──停點直讀────▶ 盤面組件（純渲染 View(game, width)）
  持有 instance + 容器
  每跑一個單位 Emit 一拍行組──▶ 事件日誌（敘事）＋步進節拍＋golden 素材
```

- 暫停機保證「前端在看畫面時，引擎必停在事件邊界」（見上方 TUI stepper），盤面組件以唯讀直讀 `*cores.Game` 渲染；**不持有規則狀態的第二份拷貝**——沒有第二份，就沒有同步問題，新顯示需求＝補一個唯讀讀取器＋渲染，不再為畫面加發任何東西。
- **日誌流的角色就是三件事**：敘事（引擎直出最終中文日誌行，消費端零解析零合成）、步進節拍（一個語意單位＝一拍＝0..n 行）、golden 素材（同 seed 同輸入＝同行序列，diff 人眼可讀）。
- 直讀的代價與守則：停點狀態必須「畫得出來」（發射點一律變更完成才發射，M18 接線原則）；組件對 `*cores.Game` 唯讀靠紀律（不另立唯讀介面，被咬到再立）。

**日誌行合約（M24 拍板；原 `EventData` 八類事件合約＋journal 行合成器退役）**：`Presenter.Emit(line ...string)`——行由 `cores` 發射台（`emit.go` 的組行原語）組畢、發後不改；行角色看首字，消費端唯一要懂的「結構」就是字面（上色即看首字）：

## 七、測試策略

統一用 **testify suite**（`Suite{Feature}` + `this` receiver），對齊 DiceBattle。

### 7.1 一律 in-memory builder（三層同一心智模型）

✅ **三層測試全部用 in-memory builder 直建資料**（不採 embedded fixture、不採 scenario/golden DSL）。
三層只差「建多少、跑多深」：

| 層 | 建什麼                                                    | 跑什麼                                           | 驗什麼             |
|:---|:----------------------------------------------------------|:-------------------------------------------------|:-------------------|
| L1 | 幾個 entity（builder）                                    | 直接戳子系統（exprs／command／selector／effect） | 單點行為           |
| L2 | entity + 初始容器                                         | 單一 phase／獨立流程（啟動技能／執行結算）       | 流程片段           |
| L3 | 完整資料 + 初始牌堆／排隊／前置技能 + scripted `Operator` | `games.Run` 跑到結算                             | 最終盤面／事件序列 |

理由：沒有重播需求、主要作者是工程／AI（非企劃），scenario 檔的好處用不到；單一做法心智負擔最低、type-safe、refactor 友善。

### 7.2 核心紀律：共用工廠，不共用實例

上一個專案用 `testdata/prefab*` 共用**建好的實例**，後期出現兩個病：①搞不清某筆資料為誰存在 ②一改壞一片。
根因是 tests 透過共用的**可變實例**互相耦合。對策——**去重去在「builder + 預設值」這層，不要去在「實例」這層**：

- builder 給一個**中性合法預設**（空白卡／普通顧客／無效果效果），test 只 inline 寫**它在乎的欄位**，其餘吃預設。
  - → 「為何存在」自明：被 set 的就是這 test 的重點，沒 set 的就是「不在乎」。
  - → 「改一個壞一片」消失：tests 各自 build、不共用可變實例，物理上互不影響。
  - → 去重沒丟：預設值吸收 boilerplate，重複量小且安全。
- **共用範圍越窄越好**：test-local ＞ 同檔／同 suite local ＞ 全專案。禁止再養全域 prefab 垃圾吸鐵；
  「一族相關 test 的共同基底」放在那個 test 檔／suite 內。
- builder **自動發唯一 ID**；test 用變數綁引用（`card := build.Card().Effect(effA)`），不手管全域 ID 表。
- 只共用「工廠／預設值／角色明確的填充料」（如 `build.FillerCard()`），不共用「帶劇情的實例」。

### 7.3 共用測試基建（放 `internal/tester` package）

✅ 已落地 `internal/tester`（取代原根層 `testdata/` 規劃）：跨包共用、只用 `cores` 公開介面；
`cores` 白箱測試不能 import `tester`（成環），自持私有複本。
**內容是工廠與替身，不是 prefab 實例庫**：

- `BuildSheet()`：迷你 in-memory 靜態表（座位／卡牌／效果／技能／抽獎／顧客）；各層測試共用同一份、只關注自己用到的列。
- `BuildData()`：包裝成 `cores.Data`（無命令編譯；自訂編譯效果以 `Data.SetEffect` 注入）。
- `FakeOperator`／`FakeRander`：決定性替身（Pick 取候選前綴、`Intn` 固定、`Shuffle` 恆等、`Weighted` 取首位）。
- `ScriptOperator`：腳本化輸入替身（M29）——各決策點依佇列消費：出牌每玩家行動階段一筆（筆內為卡牌編號序列，取首張同號手牌、查無略過、筆盡即該階段玩家結束），三類選取（選顧客／選卡牌／棄牌）每次一筆候選索引（越界略過、空筆＝棄選）；佇列耗盡回退 `FakeOperator` 行為，腳本有限故一局必然收斂。腳本形態為 Go slice 直建（依 7.2 不採 scenario DSL）。

L3 基建之日誌流錄製已備（`tester.RecordPresenter`，M17 事件版、M24 換軌為行組版：`Line [][]string` + `Flat()`）且全引擎發射點已接線並逐行釘住行文（M18 接線、M24 字串斷言）；scripted `Operator` 輸入佇列已落地（M29 `ScriptOperator`，見上）；初始盤面組裝已由關卡表格 + `StageID` 取代（M15）。
**行歷史 golden 已常駐**（M24 拍板④）：`internal/games/golden_test.go` + `internal/tester/golden_{關卡}_{seed}.txt`（快照檔與其錄製來源 `BuildSheet`／替身同放 `tester`；2026-06-12 自 `games/testdata` 搬遷）——固定 seed×關卡跑完整營業，引擎直出的行序列與快照逐 byte 比對；改文案＝`-update` 重錄（diff 可審閱）。M29 補上輸入腳本維度：關卡 604（腳本劇情）以 `ScriptOperator` 三 seed 入網，出牌／新選顧客／新選手牌／手牌上限棄牌／觸發與常駐入列（含啟動／結束命令）皆釘進快照；**決定性 CI** `.github/workflows/ci.yml` 跑 Go 三件套——lint（golangci-lint 釘本機同版）、`go test -race ./...`（`-race` 本機無 gcc 跑不了，由 CI 補）、表單檢查（`roditool sheet`）；只在合併回 `dev` 後觸發（push to dev），release workflow（v tag）以 `workflow_call` 重用同三檢後打包遊戲安裝壓縮包出 release；文件鏈留本機不入 CI。
單一 seeded `Rander` 確保 L3 決定性、assertion 穩定。

## 附錄：企劃驗證器

給**企劃（非工程）**在不跑遊戲下，檢查自己填的表格欄位有無錯誤的開發工具。M28 已落地（站序詳見第九節）：`app/roditool`（檢查引擎）＋ `cmd/roditool`（瘦進入點）。

**兩個工具＝同一引擎的兩種輸入模式**：

- **單筆檢查**：企劃貼一段內容、選欄位種類（運算式／命令／門檻配對）→ 回報帶位置的中文錯誤＝ `roditool expr|command|threshold <內容>` 三子命令（通過印 通過、不通過回非零結束碼）。
- **表單檢查**：讀 `sheetdata/` 的 json（與引擎同路徑 `infra.Load`）逐表逐欄檢查 → 輸出 表／列（編號）／欄 + 錯誤＝ `roditool sheet [--data]`，掛 `gamedata/build.bat` 尾步（表格建置後自動檢查，dev 的 `task sheet` 與遊戲安裝壓縮包同用一份）；逐筆列印、發現問題回非零結束碼（固定表序＋列編號升序，輸出決定性、可供 CI 把關）。

**三種文法，依欄位種類分派驗證**（這是整套的關鍵約束）：

| 欄位                                                   | 文法                                 | 驗證來源                                                                        |
|:-------------------------------------------------------|:-------------------------------------|:--------------------------------------------------------------------------------|
| 觸發條件 `TriggerCond`、觸發次數 `TriggerCount`        | 運算式                               | `exprs.Parse` ＋ `games.ValidateExpr`（詞彙查名＋參數數量）                     |
| 立即／觸發／啟動／結束命令 `Command*`                  | 命令（verb + 命令對象 + 內嵌運算式） | `games.Parse` ＋ `games.Validate`（含內嵌算術式走訪）                           |
| 顧客 `SateSkillID`／`CalmSkillID`（`門檻值^技能編號`） | 門檻配對                             | `cores.ParseThreshold`（與引擎載入共用單一格式來源）＋ 技能編號參照（表單檢查） |

**「語法正確」＝ Parse ＋ Validate**：文法解析之外，含詞彙查名（屬性／動詞／命令對象／查詢函式／內建函式／引用屬性）、參數數量校驗（命令對象 arity、查詢函式定數、內建函式下限）、引用基底合法性（`HasObjectRef`，左值與運算式同閘）——只做 Parse 會漏 `morale2 -= 1` 這類詞彙錯。引擎自身的載入／編譯／求值對同批資料一律寬鬆（跳過／no-op／評估失敗），嚴格把關只在驗證器。

**表單檢查的逐表項目**——通則：參照欄 `0`／空＝未指派，合法、跳過該筆；非 0 編號必須存在於目標表；字串欄空＝未填，合法（Sheeter 空字串欄生成的 `[""]` 視為空）。編碼欄的數字對照以營業規格書【四、表格結構】為準：

| 表      | 檢查項目                                                                                                                                                                                                                                                                                                                                                 |
|:--------|:---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| award   | `CardID` → card.ID                                                                                                                                                                                                                                                                                                                                      |
| card    | `SkillID` → skill.ID（`0`＝無技能）                                                                                                                                                                                                                                                                                                                     |
| effect  | `Kind`／`TargetKind`／`TriggerAfter`／`StackTime` 編碼範圍；`TriggerKind` 非空時 ∈ 觸發時機英文名稱（`cores.TriggerKindLegal`）；運算式／命令欄依上表文法驗證；適用類型矩陣（營業規格書【四、表格結構】）——當前類型不適用的欄位填了值即報；反向必填僅驗單格：觸發類型缺 `TriggerKind`（永不觸發、無合法解釋），其餘空欄有合法預設語意或標記用途、不驗 |

**工程決策**：

- **地基入 M5、工具本體為 M5 後置支線**：4／6 欄位是命令文法，命令解析器正是 M5 的核心產出。M5 驗收即要求命令解析器重用共用錯誤型別、吐友善位置錯誤（地基）；工具本體（CLI＋掃描器＋`task`／CI）依賴 M5 完成，作為非 gating 支線、可與效果系統（M10 起）並行。不先出「只驗運算式」的半套——半套掃描會讓命令欄位默默跳過，企劃看到「全部通過」會誤判命令欄也驗過了，比沒有更糟。
- **錯誤對企劃友善**：帶位置（「第 N 字附近」）、中文白話、去工程術語。`exprs` 與命令解析器**共用同一「帶位置錯誤」型別**，兩種文法的錯誤格式一致。
- **放置**：文法／錯誤型別等能力在核心（`exprs`／`games`）；前端（CLI＋掃描器）掛 `app/roditool` + `cmd/roditool` + `gamedata/build.bat`（建置後自動表單檢查）。表單檢查的文法欄與單筆檢查走同一組入口（`CheckExpr`／`CheckCommand`／`CheckThreshold`），不雙寫驗證路徑。
- **詞彙 metadata＝entry 小 struct**（M28 拍板）：rules 詞彙表 map 值升級為小 struct（`selectorEntry`／`attrReadEntry`／`attrRefReadEntry`／`builtinEntry`），行為與 metadata（arity／ref／minArg）同詞條單一定義點不漂移；述詞 `SelectorArity`／`AttrReadArity`／`AttrRefReadArity`／`BuiltinMinArg`／`HasObjectRef` 供 games 靜態查名與參數數量。引擎 `rules.Register` 只裝備行為，metadata 屬 Validate 期靜態知識、不入 `Game`。每詞條一具名函式不變。
- **不做帶參數求值 + 運算過程**：輸入 UX 難規劃，企劃用 營業規格書 + AI 可達等效，暫不納入。
- **不做參數型別靜態校驗**：參數為算術式、值型別屬執行期知識，數值檢查仍由執行期參數校驗把關。

**錯誤地基（已完成）**：`exprs` 的 `token` 已帶位置欄位、lexer／parser 錯誤改吐「第 N 字附近」中文白話、去掉 `expr:` 內部前綴；並已立 `exprs.SyntaxError`（`Pos`＋`Msg`）作為 `exprs` 與命令解析器（M5 `parse.go`）／門檻配對（`cores.ParseThreshold`）共用的帶位置錯誤型別，三文法錯誤格式一致。M28 R4A 起 `exprs` 名稱節點（識別子／函式／引用）帶來源位置、`Expr.Names()` 走訪供 `games.ValidateExpr` 詞彙查名；命令內嵌算術式（右值／參數／命令對象參數）的詞彙錯誤經 AST 記錄的偏移回算至命令座標。
